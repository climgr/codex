name: Local System Management Zone
description: Rules that relax under ~/Projects/local/system/** for managing other repos, servers, and systems
type: user
---

Repos under `~/Projects/local/system/**` are personal project/infra/fleet-management tooling (managing other repos, servers, systems) — not shippable products. **Only the five exceptions below relax; every other rule in `AGENTS.md` and its referenced memory files stays in full force**, including git safety, `security_conventions.md`, and all CI/CD, Makefile, language, and framework tooling conventions (test gates, lint gates, build rules).

**Relaxed here — nothing else:**
- **Plaintext credentials allowed** — tokens/passwords/API keys may be stored in plaintext (inventories, `.env`-style credential stores) without the SHA-256 hashing/masking `sensitive_data.md` normally requires. Full condition: `~/.codex/memory/sensitive_data.md` → "The Only Exception".
- **`LICENSE.md` not required** — every other `project_files.md` root-file requirement (`AI.md`, `IDEA.md`, `AGENTS.md`, `README.md`, `Makefile`, `.gitignore`, etc.) still applies.
- **systemctl lifecycle commands pre-authorized** — `start`/`stop`/`restart`/`reload`/`reload-or-restart`/`try-restart`/`enable`/`disable`/`reset-failed`/`daemon-reload` run without per-call confirmation (see `AGENTS.md`'s "Code & Files" → "systemctl gate" for the exact list and rationale).
- **Cross-repo / host-config access with recorded consent** — this is the point of the zone: a project here may write outside `{project_dir}` (other repos, host config files including `/etc/**`) once the user has explicitly authorized that specific path/repo for that project. A verbal "yes" in conversation is not durable and does not survive compaction — before acting, write the grant into `{project_dir}/.codex/config.toml` as a real permission entry (gitignored, machine-local). The recorded entry, not the conversation, is what pre-authorizes future access to that path without re-asking each session. Each external path/repo needs its own explicit grant — authorizing one never implies another, and nothing is inferred. Every other safety rule still applies to what's reached this way: destructive-op confirmation (`rm -rf`, force-push, etc.), git safety, and the systemctl gate (including its zone exception above) all apply identically whether the target is inside or outside `{project_dir}`. **Commit and push are never covered by any per-path grant** — see the next bullet: `gitcommit` is the sole commit+push path everywhere, zone included, with no raw-git carve-out for either.
- **Raw standard git commands pre-authorized except `commit`/`push`; the `gitcommit`-only path is lifted for everything else** — inside the zone, ordinary git commands (`status`/`diff`/`log`/`add`/`pull`/`fetch`/`checkout`/`branch`/`merge`/`stash`/`remote`/etc.) run directly, without going through `gitcommit` and without per-call confirmation — the point of the zone is managing many repos' git state directly. **`git commit` and `git push` (any form, including `-m`/`--amend`) are excluded from this pre-authorization everywhere, including here** — the user signs every commit and `gitcommit` handles that signing automatically, so raw `git commit`/`git push` are never used, in the zone or out of it; use `gitcommit --dir <path> all` instead, even for a zone repo. Mechanically enforced by `zone-git-commit-push.sh`, which has no zone exception for either subcommand. Every repo under the zone is expected to carry a `.no_push` file so `gitcommit` never actually reaches a remote from it — this is the mechanism that replaces "raw push allowed here," not an exception to the ban on raw push. **Also excluded from raw pre-authorization — always confirm first, per the global destructive-op rule, and never pre-run even here:** `git reset` (any form — `--hard`/`--mixed`/`--soft`), `git clean -f*` (`-n`/`--dry-run` is exempt — it only lists what would be removed, discarding nothing), `git push --force*`/`--force-with-lease`, `git branch -D`, `git rebase`, `git filter-repo`/`filter-branch`, `git tag -d`, `git stash drop`/`clear`, `git push --delete`, `git update-ref -d`, `git reflog expire`, `git gc --prune`, and any other command that discards commits, discards uncommitted work, or rewrites history.
  - **`.no_push` is the default for every zone repo** — create it (`touch .no_push`) as soon as a repo under `~/Projects/local/system/**` is created or found without one, so a `gitcommit --dir <path> all` there ever only commits, never pushes. This is the normal case, since these repos are personal project/infra/fleet-management tooling with no publishing need.
  - **Repo privacy gate** (the opt-in case — a named zone repo that does need a pushed remote, overriding the `.no_push` default and the general `local` provider's "no remote" default for that one path): only under this sequence — never auto-create a remote, never leave `.no_push` in place while intending to push:
    1. If no remote exists yet, create it explicitly with `gh repo create --private` (or provider equivalent) — never let anything auto-create it, since auto-create does not guarantee private visibility.
    2. Remove any `.no_push` file from this repo — its presence would otherwise silently swallow the push in step 4.
    3. Review the local diff/status for secrets/PII before committing — the zone's plaintext-credential exception means a diff can legitimately contain real tokens/passwords; confirm nothing that should stay local, or still needs masking outside the credential-store files it's meant for, is about to leave the machine.
    4. Re-verify visibility immediately before committing — `gh repo view {org}/{repo} --json visibility` (or provider equivalent); only if `private`, proceed.
    5. Run `gitcommit --dir <path> all` — this both commits (signed, automatically) and pushes in one step; there is no separate raw-commit-then-push split, since raw `git commit`/`git push` are never used even here.
    6. Re-verify visibility after every push; if a repo is ever found public, switch it to private immediately (`gh repo edit --visibility private` or provider equivalent) before continuing any other work.

**Still hard — no exception, ever, even with a recorded grant:**
- `gitcommit` is the only commit **and** push path everywhere, including inside the zone — the raw-git exception above never covers `commit` or `push`, only the other git commands listed. A zone repo that must never publish relies on its own `.no_push` file, not a raw-git carve-out, to make that permanent
- `systemctl mask`/`unmask`/`edit`/`set-property`/`isolate`/`kill` and all other `security_conventions.md` rules
- **Core OS paths are never a valid grant target, regardless of consent** — `/`, `/boot/**`, `/sys/**`, `/proc/**`, `/dev/**`, partition tables, and bootloader config. This is the "system dir" floor — infra config (`/etc/**`, service configs, other repos) is in scope; the kernel/boot/device layer is not.
- All CI/CD, Makefile, language, and framework tooling conventions
